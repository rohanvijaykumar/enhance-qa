# The `qa/` folder

Plain Markdown, so agents and people can both read and edit it, and git shows clean diffs. `qa init` creates it from `templates/qa/`.

```
qa/
├── README.md        what this folder is and how to edit it (written once)
├── STATUS.md        the dashboard (generated by `qa status --write`; tick boxes and answer questions here)
├── plan.md          the test plan, plus settings in the front matter
├── notes.md         the testers' handbook: how to start the app, log in, reach each area; quirks
├── coverage.md      when each check last ran and its result (generated by `qa coverage`)
├── checklist/       one file per area: auth.md, cart.md, accessibility.md, …
├── bugs/            one file per bug: BUG-001.md, …
├── runs/            one file per pass (007-check.md), plus a folder per run for tester notes (007/)
├── evidence/        screenshots, recordings and logs, by run (git-ignored by default)
└── .state/          lock, build registry, hashes, the current phase, saved test logins (git-ignored)
```

A monorepo or a product with several apps gets one folder per app: `qa/<app>/` with the same layout. `qa/plan.md` at the top lists the components.

## Who writes what

| Path | Lead | Scout | Tester | Verifier | Fixer | User |
|---|---|---|---|---|---|---|
| `qa/plan.md` | yes | yes | — | — | — | yes |
| `qa/notes.md` | yes (merges what testers learn) | yes | — | — | — | yes |
| `qa/checklist/**` | regression checks only | yes | — | — | — | yes |
| `qa/bugs/**` | yes (files, triages, copies verification logs with `qa bug log`) | — | — | — | fix notes only | yes |
| `qa/runs/**` | yes | — | own notes only (`runs/<run>/tester-<n>.md`) | own notes only (`runs/<run>/verifier-<n>.md`) | own notes only (`runs/<run>/fixer.md`) | yes |
| `qa/evidence/**` | yes | yes | yes | yes | yes | yes |
| `qa/STATUS.md`, `qa/coverage.md` | via scripts | — | — | — | — | ticks and answers |
| product code and tests | — | — | — | — | yes | yes |

`qa gate` enforces this after every phase (`qa phase start --role <role>` records the starting point).

## Git

- `qa/` is meant to be committed with the project, so the QA history travels with the code and a team shares it.
- `qa init` adds `qa/evidence/` and `qa/.state/` to `.gitignore`. Evidence can be committed instead if the user wants (`evidence: commit` in the plan).
- QA never commits `qa/` changes on its own unless the user turns that on (`commit_qa: yes` in the plan). Fix commits contain code and tests only.

## `.state/` files

| File | What |
|---|---|
| `lock.json` | The run lock: run number, start time, host. Stale after 6 hours |
| `builds.json` | Build numbers mapped to the snapshot commit, the branch commit (`head`) and the tree |
| `hash.json` | The checklist hash recorded at the start of the run |
| `phase.json` | The current phase: role, starting tree, allowed paths. Hooks read it; with no phase file, hooks do nothing |
| `sessions/` | Saved test logins (cookies, storage state) for the drivers |
| `backup/` | File backups for fixes when there's no git |

## Editing rules

- **The user can edit anything, any time between runs:** add a check, change an expectation, re-prioritise a bug, tick a human check. The next run picks it up.
- **IDs are permanent.** Never renumber. A check that no longer applies gets `Retired: <date> <reason>` and stays in the file.
- **`qa validate`** reports format problems instead of guessing. It checks that IDs are unique, required fields are present and statuses are valid.
- **Exports on request:** `qa export csv`, `qa export html`, and `qa export xlsx` (needs Python with openpyxl).
